2.1 Обязательный пре-чек перед отправкой любого утреннего письма
    can_send_morning_letter(contact_hash, house_id, has_partner_spotlight)
---------------------------------------------------------------------------

Система проверяет ПОСЛЕДНЮЮ запись в consent_logs по связке
(contact_hash, house_id, kind) — отдельно для каждого kind.

Отправка разрешена только если одновременно:

  1) kind = 'ads':
     последняя запись существует И is_granted = TRUE.

  2) Если письмо содержит спотлайт чужого дома
     (не отправляется от имени исходного дома по своей базе как чистое
     письмо дома без чужого спотлайта):
     kind = 'partner_spotlight':
     последняя запись существует И is_granted = TRUE.

  3) Ни по одному из задействованных контуров (ads и, при спотлайте,
     partner_spotlight) нет более свежей записи с is_granted = FALSE (STOP).
     Практический смысл: «последняя» строка уже должна быть TRUE;
     любая более новая FALSE блокирует. Нет записи = нельзя слать.

Политика STOP (зафиксировано): один клик пишет ДВЕ строки FALSE —
  kind='ads' И kind='partner_spotlight' (одна транзакция):

  INSERT INTO consent_logs (contact_hash, house_id, kind, offer_version,
                            is_granted, source_channel, ip_address)
  VALUES
    (:contact_hash, :house_id, 'ads', :current_offer_version,
     FALSE, 'email_stop_link', :client_ip),
    (:contact_hash, :house_id, 'partner_spotlight', :current_offer_version,
     FALSE, 'email_stop_link', :client_ip);

  Итог: can_send_ads=FALSE и can_send_spotlight=FALSE в v_consent_current.

Канон БД для ворот: VIEW v_consent_current
  (DANTE-FLORENS-DDL-W1-CONSENT-DEALS.sql §3)
  письмо без спотлайта → can_send_ads = TRUE
  письмо со спотлайтом → can_send_spotlight = TRUE
  нет строки view (нет ads) → нельзя слать

Инвариант ядра:
  Утренний воркер / сборщик пачки ОБЯЗАН вызвать can_send_morning_letter
  (или читать v_consent_current) на каждый контакт.
  Обход пре-чека = дефект DoD (блокирующий баг).

Рекомендуемая сигнатура сервиса (псевдо):
  can_send_morning_letter(contact_hash, house_id, opts) →
    { ok: boolean, reason?: 'no_ads'|'ads_stop'|'no_spotlight'|'spotlight_stop' }


2.2 Эндпоинт мгновенного СТОП
---------------------------------------------------------------------------

  GET|POST /api/v1/public/stop/{signed_token}

Требования:
  • Не требует авторизации и ввода пароля (публичный one-click / письмо).
  • signed_token: HMAC/JWT с contact_hash (или opaque id), house_id,
    kind(s) к отзыву, expiry; без утечки сырого телефона/email в URL
    предпочтительно opaque id → lookup на сервере.
  • В одной транзакции пишет ДВЕ строки в consent_logs:
      is_granted = FALSE, source_channel = 'email_stop_link'
      kind = 'ads' И kind = 'partner_spotlight'
      offer_version = :current_offer_version
      (канон SQL — блок выше / §2.1)
  • SLA записи: < 200 мс (p95 целевой).
  • Инвалидирует контакт в очереди текущей невыпущенной утренней пачки
    (удаление/флаг skip до отправки).

Ответы:
  200 — STOP принят (идемпотентно: повторный клик = ещё одна FALSE-строка
        или no-op с 200, если уже STOP; предпочтительно идемпотентный 200).
  400 — битый/просроченный токен.
  404 — неизвестный токен.
  Тело ответа: нейтральная HTML/JSON страница «Вы отписаны» без ПДн.

2.4 Эндпоинты жизненного цикла сделки
---------------------------------------------------------------------------

A) POST /api/v1/deals
   Создание сделки от имени Дома А (инициатор).
   Auth: Хозяин дома (узел).
   Тело (минимум): partner_house_id, amount_rub, thread_id?, note?
   Поведение:
     • status = 'pending_partner'
     • house_a_confirmed_at = NOW()
     • house_b_confirmed_at = NULL
     • network_fee_rub = 0
   Не создаёт проводку в treasury_ledger.
   Не попадает в Data Room / инвесторский оборот.

B) POST /api/v1/deals/{id}/confirm
   Вызов от имени второго дома (house_b).
   Auth: Хозяин дома B (должен совпадать с partner по сделке).
   Поведение (одна транзакция БД):
     1. Проверка status = 'pending_partner' и caller = house_b.
     2. house_b_confirmed_at = NOW()
     3. status = 'double_confirmed'
        (триггер fn_deals_before_save выставляет house_b_confirmed_at при
         необходимости и network_fee_rub = ROUND(amount_rub * 0.08, 2);
         нулевой чек → fee = 0.00, CHECK допускает fee >= 0)
     4. INSERT в treasury_ledger (проводка сети / казны; при fee=0 —
         политика: либо нулевая проводка, либо skip ledger — зафиксировать
         в коде как «ledger только если fee > 0»).
   Ошибки:
     403 — не второй дом / нет прав
     409 — уже confirmed / disputed / неверный статус
   Запрет: INSERT сразу в double_confirmed в обход confirm (триггер
   проставит обе метки — дыра; закрывать auth-слоем).

Дополнительно (неделя 1–2, минимально):
  POST /api/v1/deals/{id}/dispute — перевод в disputed (суперадмин
  или любой из двух домов по политике; арбитраж вне казны).


2.5 Системные инварианты (сводка DoD спринта)
---------------------------------------------------------------------------

I1  Нет can_send → нет строки в исходящей утренней очереди.
I2  STOP пишет только INSERT в consent_logs; UPDATE/DELETE невозможны.
I3  Сырой экспорт контактов недоступен house_owner и city_curator.
I4  treasury_ledger и Data Room читают только deals.status =
    'double_confirmed'.
I5  network_fee_rub до confirm = 0; при double_confirmed считает
    триггер (8% от amount_rub, допускается 0).
I6  Тексты согласий в UI/виджетах ссылаются на offer_version
    'v1.0-2026-11' (см. §3); код не хардкодит юридический текст.

3. Параллельный трек для юриста (Бриф на Спринт 1)
--------------------------------------------------------------------------------

Цель: не блокировать разработку DDL/API. Юрист готовит 3 независимых
текста под версию:

  offer_version = v1.0-2026-11

Текст 1 — kind = 'pdn'
  Согласие на обработку персональных данных оператором (Домом)
  с указанием цели и срока.

Текст 2 — kind = 'ads'
  Согласие на получение информационных и рекламных сообщений от Дома
  (ст. 18 ФЗ-38 «О рекламе»).

Текст 3 — kind = 'partner_spotlight'
  Отдельное предметное согласие на получение партнерских предложений
  в рамках утренних дайджестов сети «Данте Флоренс»
  без передачи контактных данных третьим лицам.

Требования к артефакту юриста (сдать в репозиторий legal/ или админку):
  • три файла/записи с точным текстом на момент акцепта;
  • версия v1.0-2026-11;
  • чекбоксы раздельные, не предустановленные;
  • формулировка STOP / отзыва;
  • кто оператор (Дом) vs сеть (обработка по поручению / без передачи
    сырой базы — согласовать с Текст 3).

Пока тексты не утверждены:
  продукт пишет в consent_logs offer_version = 'v1.0-2026-11-DRAFT'
  и не включает боевую рассылку в пилотный город.
